# Foundation setup — what's here and what's next

This page explains, in plain words, the new "plumbing" we added so the app can
move to a safer, faster setup. A new developer should be able to read this and
understand it. The full plan lives in
`C:\Users\User\.claude\plans\go-through-each-page-cosmic-sutherland.md`.

## The big picture (why we're doing this)

Today the app talks to **Supabase** directly and **anyone can call the write
APIs without logging in**. We are fixing that by adding, one safe piece at a
time:

| New tool | What it does (like…) |
|---|---|
| **Prisma** | A typed, safe way to talk to the database (a translator) |
| **Neon / VPS Postgres** | Where the data lives (staging on Neon, production on your server) |
| **Better Auth** | Handles login + 2FA properly (a professional doorman) |
| **Upstash Redis** | Super-fast memory for sessions, rate limits, caching (a sticky-note board) |
| **Cloudflare R2** | Where uploaded files live (a filing cabinet) |
| **TanStack Query/Table** | Loads and shows data on screen cleanly (a smart waiter) |

We flip between old and new with two switches in `.env.local`:
`DATA_BACKEND` (`supabase` → `prisma`) and `AUTH_PROVIDER` (`legacy` → `betterauth`).
This means **the app keeps working** the whole time.

## Handy commands

```bash
pnpm dev            # run the app
pnpm db:pull        # read the existing DB into schema.prisma (Step 2)
pnpm db:generate    # regenerate the typed client after schema changes
pnpm db:migrate     # create/apply a migration (Step 2)
pnpm db:studio      # open a visual table browser
pnpm typecheck      # check TypeScript
```

## What's DONE (Step 2) — Prisma schema + Neon + data transfer ✅

- ✅ `pnpm db:pull` read the **25 live tables** from Supabase into
  `prisma/schema.prisma` (kept the original snake_case table/column names).
- ✅ Reconciled two DB-only details so Neon can build the tables:
  - `schools.school_id` was generated by a Supabase function
    (`generate_school_id()`); that function doesn't exist on Neon, so the **app**
    (school repository) will generate this code from now on.
  - `teachers.attendance_percentage` was a computed column; it's now a plain
    column the teacher repository keeps updated.
- ✅ Kept the `schools` composite primary key as-is (all foreign keys point at
  the unique `id`, so there was no need to risk changing it).
- ✅ `prisma db push` created all 25 tables on **Neon** (staging).
- ✅ Baselined a migration (`prisma/migrations/0_init`) and marked it applied, so
  production (the VPS) can use `pnpm db:deploy` going forward.
- ✅ `pnpm db:transfer` copied **all data Supabase → Neon: 1,864 rows across 25
  tables, every table source = target**. (`scripts/migrate-data.ts`.)

> Note on what is NOT carried to Neon: Supabase **row-level security (RLS)** and
> **CHECK constraints**. That's intentional — we now enforce those rules in the
> app with Zod (`lib/validation/*`) and the repository layer, which is simpler
> and is the approach the plan chose. The old `notifications`, `activity_logs`,
> `login_history`, and the subjects "command-center" tables (assessments,
> curriculum, resources) **did not exist** in the live database — they are
> Phase 3 work.

## What's DONE (Step 3–4 core) — repository + the security guard ✅

The safe "doors" to the database are built and **proven end-to-end**:
- ✅ `lib/repositories/teacher.repo.ts` — the first repository. Only repos import
  `lib/db/prisma.ts`. It takes `schoolId` and filters by it.
- ✅ `lib/api/guard.ts` — `requireAuth()`: checks the session (the existing
  `stackable_session` cookie), role, page permission, and rate limit. Returns
  `{ userId, schoolId, role }`. *(The session check is a clearly-marked seam we
  swap for Better Auth in Step 7.)*
- ✅ `GET /api/teachers` wired to the guard + repo behind `DATA_BACKEND=prisma`.

**Verified by running the app:**
| Request | Result |
|---|---|
| No login | **401** "You must sign in." (the old hole is closed) |
| Logged in, old backend | 200 — 50 teachers (all schools, the old leak) |
| Logged in, `DATA_BACKEND=prisma` | 200 — **only the user's school's teachers** (leak fixed) |

Also: a clean dependency reinstall fixed earlier module-resolution problems, so
**`pnpm typecheck` now passes with 0 errors** across the whole project.

## What's DONE (Step 5, 7, 8 — via coordinated specialists) ✅

- **Step 5 (route security):** `requireAuth` now guards **17 routes**. The ONLY
  unguarded routes are the intended public ones: `auth/*`, `jobs/send-otp-email`,

  `AUTH_PROVIDER=betterauth`.
- **Step 8 (TanStack — started):** `QueryProvider` mounted in `app/layout.tsx`;
  `hooks/useTeachers.ts` created; the teachers list page now loads via TanStack

**Verified:** `pnpm typecheck` = 0 errors · app boots · home/login/teachers pages

- **Step 9** — cutover: flip `DATA_BACKEND`/`AUTH_PROVIDER`, delete legacy code.

## ⚠️ Security: rotate the old keys
The current `.env.local` holds **live** secrets (Supabase service-role key,
Resend, QStash, Pingram, Infobip). Because the write APIs aren't protected yet,
that Supabase key is especially sensitive. Please **rotate these keys** in their
dashboards and update `.env.local`. (`.env*` is already git-ignored, so they are
not in source control — good.)
